# 短句默写模式 + 选词表描边修复 + 准备进度阶段化（2026-10-17）

本轮的三个议题来自崔总同一次反馈：

1. 选词表弹层里「使用中」那一行的左边框被切掉；
2. 准备阶段（生成语音 / 生成题）的进度条是否正常；
3. 新增**短句**默写模式，放在「组句」左边；并追加约束：**句子要短、允许不是完整句子**。

方案见 `plans/sentence-mode.md`（含 6 个决策点的确认记录）。

> **同日修订（崔总 2026-10-17）**：短句模式的播报、判定与计时又改了三处，均已落地：
> ① 只念整句 **3 遍**，不再先念目标词（用户听到第一个音就开始写，念单词没有用）；
> ② 判定改为**整句匹配**（忽略大小写；空格与标点必须对上），AI 批改降级为「差在哪」的参考备注；
> ③ 计时改为**整句基础公式**（3 遍 ×（4s 思考 + 0.45s × 整句字符数，含空格标点）），
> 属基础计算方式调整，没有动用三档速率/倍率这类系数。详见下方 §三、§四。

---

## 一、选词表左边框被切（已修）

### 根因（实测几何）

选中行用 `ring-[1.5px]`（Tailwind 的 ring 是**画在盒子外面**的 box-shadow），而列表在
`overflow-y-auto` 容器里 —— 按 CSS 规范，`overflow-y:auto` 会让另一轴也退化为 `auto`，
从而裁剪两个方向。浏览器实测：

```text
行 left=268，滚动容器 left=268   → 行左边缘与容器齐平，ring 有 1.5px 落在容器外
容器 padding: 0px / 4px          → 右侧那 4px 正好容下 ring（所以右边看起来正常）
```

### 改法

`BankPickerDialog` 的 `Row` 选中态改为 `border-[1.5px] border-brand`（画在盒子内，
任何容器都裁不到），未选中保留**同宽透明边框**，保证切换选中项时行高与文字不位移。
`ClozeView` 里同样的 ring 在 `p-5` 容器内、不滚动，无此问题，未改动。

## 二、准备阶段进度条（已确认 + 改造）

### 实测（无头浏览器逐 200ms 采样真实后端）

| 阶段 | 请求形态 | 实测表现 | 结论 |
| --- | --- | --- | --- |
| 生成语音 | **每 4 词一批**，多批 | `0% → 40% → 80% → 100%` | 正常，确实是多次请求 |
| 组句「正在出题」 | **单次** AI 请求 | 卡在 0% 达 **33 秒**（另一次直连 12.3s） | 像卡死 |
| 释义/中文词的 AI 段 | 单次请求，与 TTS **并行** | TTS 8.4s 就跑满 100%，之后又等 12s | 100% 仍在等，误导 |

### 改造

- `PreparingOverlay` 增加 `indeterminate`：单次请求阶段用**流动条**代替冻结的百分比，
  配套 `src/app.css` 的 `prep-indeterminate` 关键帧。
- 组句出题：进入即不确定态；拿到题目后切回确定态跑 TTS 进度。
- 释义/中文词：TTS 与 AI 并行，**TTS 完成而 AI 未完成时切成不确定态**，不再出现「100% 还在等」。
- 短句模式：生句阶段不确定态；目标词与整句两条 TTS 并行、按**合并计数**上报（`done/total`）。

## 三、短句模式（已实现）

### 决策（崔总确认）

| 决策 | 结论 |
| --- | --- |
| 播报 | **只念整句 3 遍**（修订后：不先念目标词） |
| 判定 | **整句匹配计分**（忽略大小写；空格与标点必须对上）；AI 批改只给参考备注、不计分 |
| 缺句 | 该词**降级为单词轮**，不中止本场 |
| 词形 | 允许屈折变化（`go`→`went`、`apple`→`apples`） |
| 长度 | 目标 **3–6 词**、**硬上限 8 词**；**允许片段/词组** |
| 超长 | 做一次「收紧到 ≤5 词」重试，仍不合格才降级 |

### 实现要点

- **生句链路**（与释义同构，独立文件避免格式互相牵连）
  - `src/lib/sentence-provider.ts`：提示词（短为首要要求 + 显式允许片段 + 生成级别）、
    `sentenceWordCount` / `containsWordForm` / `validateSentence`、超长与缺词判定；
  - `src/lib/sentence-service.ts`：`sentences.json` 缓存（带 `model` + `contentLevel` 失效）、
    **只缓存通过校验的项**、超长项一次收紧重试、原子写 + **写后复读**；
  - `POST /api/sentences`、客户端 `requestSentences`、`pnpm get:sentences` 诊断脚本。
- **计时**（`src/lib/timing.ts`，修订后为整句基础公式）
  - `sentenceCountdownDuration` = `(4 + 0.45 × 整句字符数) × 3`（字符含空格与标点）；
  - `sentenceSpeechIntervals` = `[思考, 思考+书写, 书写]`（三遍播报后各一段）；
  - 两者仍乘 **三档速率 × 倍率调整**——但时长本身是靠基础公式加长的（实测同一句从 18.9s 提到 45.8s 量级），
    没有靠调系数凑；
  - 双轨制不变：倒计时结束只表示「允许进入下一轮」，语音没放完继续等（因此估时不会短于音频）。
- **播放序列**（`src/lib/api.ts`）
  - `playWithIntervals` 从「同一音频重复 N 遍」升级为 `items: { url, label }[]` + 逐项间隔；
  - 短句轮 = `[整句 1, 整句 2, 整句 3]`，状态行显示标签而不再是「第 N 遍」；
  - 播放失败按**出错的那一条**淘汰缓存（原来只有单个 `audioName`）。
- **准备流程**（`src/lib/use-dictation.ts`）
  - `prepareSentence`：生句 → 缺句降级 → **只合成整句音频**（降级词才合成单词音频，少一半请求）→ 建轮次；
  - 生句整体失败（网络/额度/配置）→ 全场降级为单词轮 + 结果页提示，不白等一场；
  - `WordRound` 增加 `variant` / `sentence` / `sentenceAudioName` / `playLabels`。
- **作答与结果**
  - 赛博：一段式输入（`输入整句…`）；书写：手写整句，空格跳轮；
  - `ResultsView` 新增短句专用行：`✓ 目标词 + 发音 + 单词写对了` / `标准：…（目标词高亮）` /
    `我写：…（可换行，最多 3 行）` / `整句基本正确 · AI 备注（中文）`；
  - 判定用 `isSentenceMatch`（忽略大小写、空格与标点算），`sentence` 字段 `graded: true`；
  - 整句全对时**不再请求 AI**（省一次等待）；有出入时 AI 备注以「AI 参考：」展示；
  - 降级轮显示「本词没有合格短句，按单词默写」。
- **写回**：`ReviewMode`/`ResultFieldKind`/历史白名单都加 `sentence`（只增不改）；判定取整句匹配；
  **降级轮按 `word` 记账**（短句场次里没有 context 的行），避免污染模式维度统计。

### 额外修掉的隐患

`vite.config.ts` 把 `lucide-solid` 别名到 `src/lib/icons.tsx`，而 tsc 按真实包解析 ——
「组件用了图标、icons.tsx 忘了 re-export」在 tsc 下完全通过，运行时才炸
（本轮新增图标时就踩到：dev 下页面能渲染但**事件全部失效**）。新增

## 五、关键取舍

1. **单词判定看「整句里有没有这个词」**，而不是要求整句逐字一致：默写的目标是词，整句是语境；
   整句一致性交给 AI 批改做参考展示，两条轨互不干扰（与「单词计分 + 整句只展示」的决策一致）。
2. **降级而不是中止**：短句生成受模型稳定性影响，缺一句就废掉整场体验太差；降级后该词仍能复习。
3. **超长只重试一次**：重试能把大部分超长救回来（实测本机模型一次就合格），但反复重试会让准备时间不可控。
4. **TTS 两轨并行**：目标词与整句各自按 4 条一批并行合成（峰值 4 个连接），换来准备时间减半；
   进度按合并计数上报，用户看到的是一个总数。
5. **播放序列而非单音频循环**：短句轮必须播两种音频，序列模型同时让「哪一条坏了」可定位到缓存文件。
