# 默点啥 Web 核心业务代码审查报告（需求澄清修订版）

日期：2026-08-01

## 审查范围

- `src/lib/use-dictation.ts`：准备、逐轮默写、跳转、输入与结果编排
- `src/lib/api.ts`：TTS/释义客户端请求、音频重复播放
- `src/lib/timing.ts`、`src/lib/match.ts`、`src/lib/settings.ts`
- `src/routes/api/*`、`src/routes/word-cache/*`：TTS、释义、音频缓存服务端路由
- 与上述业务直接相关的组件和单元测试

不包含 Deno Desktop/client 外壳、Windows 打包和客户端封装。本报告已结合开发过程中补充的需求重新定性；本轮除报告、需求文档和测试外，不修改业务实现。

## 修订结论

初版报告把三项后续明确需求误判成了双轨规则缺陷，现已更正：

1. 赛博模式完成本轮全部输入后允许快速跳过剩余倒计时，这是明确需求。
2. 书写模式在未实际发声时按空格允许中止余下等待或播报并跳轮，这是明确需求。
3. 音频失败或 AI 只返回部分释义时，优先保证整场流程继续，不应因单项远程或媒体异常永久卡住。

自动推进仍采用倒计时轨和语音轨解耦；上述用户动作与容错路径是明确例外。相关规则及 `pnpm + Vitest` 测试选型已补入 `AGENTS.md`。

## 仍需处理的问题

### [P1] 释义表按普通对象取值，特殊单词键会命中原型属性

位置：`src/routes/api/definitions.ts:31-38,161-180`，`src/lib/use-dictation.ts:66-87`

释义缓存和客户端释义使用普通 `{}`，读取时直接使用 `cached[w]` / `data.defs[w]`，没有检查自有属性。`constructor`、`toString`、`valueOf`、`__proto__` 等合法词汇可能从 `Object.prototype` 得到非字符串值。

例如开启释义模式并加入 `constructor` 时，空缓存也可能被误判为已有释义；客户端随后可能把函数交给 `definitionLength`，在 `def.trim()` 处报错。这不是纯安全理论问题，`constructor` 本身是合理的英语或编程词汇。

处理建议：所有词键读取统一使用 `Object.hasOwn(record, word)` 并校验值为非空字符串；构造词键字典时使用 `Object.create(null)` 或 `Map`。缓存读入后同样做 schema 清洗，不能信任 JSON 结构。

### [P2] 音频失败会继续推进，但损坏缓存没有被淘汰

位置：`src/lib/api.ts:133-165`，`src/lib/use-dictation.ts:318-330`，`src/routes/api/tts.ts:72-84`

`audio.onerror` 和 `audio.play()` reject 当前都会结束本次播放等待，最终允许流程继续。根据补充需求，“不中断整场默写”是正确策略；问题在于调用方不知道本轮发生了媒体错误，也不会移除可能损坏的缓存，TTS 准备又只用 `existsSync` 判断缓存命中，错误文件可能被反复使用。

处理建议：

- 将播放结果从 boolean 改成可区分 `completed`、`aborted`、`media-error`、`play-rejected` 的结果；无论错误与否都允许当前轮继续。
- `media-error`、解码失败或确定的 `NotSupportedError` 触发受文件名白名单保护的缓存失效接口，删除对应文件；下次准备自动重新生成。
- `NotAllowedError` 等浏览器自动播放策略错误不应删除缓存，因为文件本身可能正常。
- TTS 写缓存前校验音频非空且具有合理媒体头，采用临时文件写入后原子 rename，避免进程中断留下半文件。
- 为单个文件设置一次失效/重试上限，避免错误服务导致删除与重建死循环。

### [P2] 中止后立刻重新开始存在旧准备任务覆盖新状态的竞态

位置：`src/lib/use-dictation.ts:105-106,154-224,227-232`

准备任务没有请求序号或当前 controller 身份校验。第一轮中止后，旧 Promise 的 catch 可能稍后无条件 `setPhase("idle")`，覆盖已经开始的第二轮准备；旧任务也可能覆盖 `rounds`、`lastPrep` 或 `ready`。

处理建议：为每次准备分配递增 token，只允许当前 token 更新进度、错误、轮次和 phase；中止时使 token 失效。所有异步回调写状态前都检查 token，而不只检查自己的 signal。

### [P2] “中止准备”没有真正终止服务端正在进行的外部调用

位置：`src/routes/api/tts.ts:69-84`，`src/routes/api/definitions.ts:211-235`

TTS 只在开始每个单词前检查请求 signal，已经进入 `EdgeTTS.synthesize()` 的任务无法中止。释义请求只使用 60 秒 timeout，没有组合客户端请求的 signal；用户中止后，AI 调用可能继续消耗网络、时间和额度并写入缓存。

处理建议：

- AI fetch 使用 `AbortSignal.any([event.request.signal, AbortSignal.timeout(60_000)])`；降级重试前再次检查客户端 signal，中止后不得发起第二次请求。
- TTS 若库支持 signal，直接传入；若库不支持取消正在执行的合成，至少立即停止调度新单词，并在合成返回后检查 signal，已中止则丢弃结果、不写缓存。
- 缓存写入前统一检查请求仍有效，避免用户中止后的后台结果污染当前准备状态。
- 区分用户中止和真实超时：用户中止不显示服务错误，超时仍可提示重试。

### [P2] AI 部分释义的容错策略需要被显式保护

位置：`src/routes/api/definitions.ts:108-119,241-254`，`src/lib/api.ts:80-97`

AI 只返回部分释义时继续进入准备完成，符合补充需求。当前服务端只把实际返回的非空释义合并进缓存，`missing` 没有直接写入 JSON，基本符合“不做负缓存”的方向；但客户端忽略 `missing`，且普通对象原型问题会破坏“是否真的有释义”的判断，因此这个策略还缺少明确的校验和回归保护。

处理建议：只缓存请求词集合中、键精确匹配且值为非空英文字符串的条目；`missing` 明确返回客户端并按缺失释义的兜底时长继续；下一次准备必须再次请求这些缺失项。不要缓存空字符串、错误码、占位文本或 missing 标记。

## 已确认正确或已解决

### 赛博模式快速跳过倒计时——符合需求

`src/lib/use-dictation.ts:264-280` 在输入完成且语音轨结束后允许忽略剩余倒计时，这是用户明确要求的快速跳过行为，不再列为缺陷。应通过生产编排测试固定该规则。

### 书写模式空格跳轮——符合需求

`src/lib/use-dictation.ts:387-396` 允许在语音未实际发声时用空格中止当前轮并跳转，包括播报间隔中的快速跳过。这是明确要求，不再列为缺陷。

### 键盘监听焦点问题——已解决

当前 `src/lib/use-dictation.ts:407-412` 已在 `onMount` 中把 keydown 监听绑定到 `window`，并在 cleanup 中移除，不再依赖焦点位于根 `div` 子树。初版报告对应问题已关闭。

### AI 部分响应继续推进——符合容错目标

远程 AI 具有不确定性，部分释义不应卡死整场准备。需要保证的是缺失项不形成负缓存、后续可重试，而不是要求本次必须失败。

## 其他需求差异

AGENTS.md 仍要求“全部默完后先显示默完了，再提供查看结果按钮”。当前最后一轮直接进入 `results`，没有独立完成态或“查看结果”动作（`src/lib/use-dictation.ts:276-280`）。该项未获得新的需求澄清，继续保留为待产品确认的流程差异。

“释义只能英文”目前主要依赖提示词。建议在缓存前做轻量的结构和字符检查；不宜因为语言检测不确定就阻断流程，但明显非英文结果不应进入长期缓存。

## 测试覆盖结论

初审时 105 个单测全部通过，但 `src/lib/state.ts` 的平行状态模型不能代表生产实际运行的 `useDictation`。本轮已补充直接针对生产编排层、音频容错和释义路由缓存策略的测试，固定以下已确认规则：

- 赛博输入完成后，语音结束即可快速跳过剩余倒计时。
- 书写模式自动推进仍需倒计时和语音均完成。
- 书写模式空格可人工跳轮。
- 释义模式必须完成单词与释义两步输入才能快速推进。
- 音频媒体错误仍结束本轮播放流程，避免永久卡死。
- AI 部分释义响应可以返回已有条目，不把远程不确定性升级为整场失败。

## 建议处理顺序

1. 修正特殊词键的释义字典读取，避免合理词汇直接破坏准备流程。
2. 保留音频失败继续推进的策略，同时增加错误分类和损坏缓存淘汰。
3. 用准备 token 隔离陈旧任务，并把中止信号贯穿 AI/TTS 服务端调用。
4. 显式保护部分释义“不负缓存、下次重试”的容错策略。
